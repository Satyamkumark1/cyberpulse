# BACKUP AND RECOVERY — CyberPulse AI

| Field | Value |
|---|---|
| Version | 1.0 |
| Key property | **The dataset is reproducible from a seed.** This changes the backup problem fundamentally. |
| Related | `devops/disaster-recovery.md`, `architecture/database-design.md` §10 |

---

## 1. What Actually Needs Backing Up

Most of this system's data is not worth backing up, because it can be regenerated byte-identically in minutes.

| Data | Recoverable by | Backup needed |
|---|---|---|
| Complaints, accounts, transactions, withdrawals, ATMs | `generate:data` with seed 26184 | **No** |
| Hotspots | Hotspot engine refresh | **No** |
| Model artefacts | `train:model`, or the previous container image | **No** |
| Schema | Migrations in version control | **No** |
| Application code and configuration | Git | **No** |
| **Predictions** | Re-running analysis | Partially — history is lost |
| **Alerts** | Nothing | **Yes** |
| **Investigations and notes** | Nothing | **Yes** |
| **Audit events** | Nothing | **Yes** |
| **Analytics events** | Nothing | Low value, but irreplaceable |

Four tables out of sixteen hold irreplaceable state, and all four are user-generated. Everything else is a function of a seed, a migration set and a git SHA.

This is a genuine architectural advantage of the deterministic generator, and it is worth stating plainly: **a total database loss costs the demonstration's alert history, not the demonstration.**

## 2. Backup Mechanisms

| Mechanism | Covers | Retention | Restore time |
|---|---|---|---|
| Neon point-in-time restore | Everything | Tier retention window | Minutes |
| `generate:data` + `db:seed` | All seed data | Permanent (git) | ~3 min |
| `train:model` | Model artefacts | Permanent | ~2 min |
| Container image in the registry | Deployed model artefacts | Registry retention | Seconds |
| Git | Code, schema, migrations, documentation | Permanent | — |
| `manifest.json` checksums | Data integrity verification | Permanent | — |

The manifest is the part people overlook. It records a SHA-256 per generated file, and seeding verifies each one before inserting — so a corrupted or substituted file is rejected rather than loaded, which is a form of backup integrity rather than backup volume.

## 3. Recovery Objectives

| Scenario | RPO | RTO | Method |
|---|---|---|---|
| Accidental data deletion | Neon retention window | < 15 min | Point-in-time restore |
| Corrupted seed data | 0 (regenerable) | < 5 min | Truncate and re-seed |
| Lost model artefacts | 0 (regenerable) | < 5 min | Retrain, or redeploy the previous image |
| Total database loss | Neon retention window | < 30 min | Restore, or rebuild and re-seed |
| Total database loss, no restore available | **All user-generated state** | < 10 min | Rebuild and re-seed; alerts and investigations are gone |
| Corrupted migration | 0 | < 20 min | Restore to before the migration, forward-fix |

The worst row is the fifth, and its consequence is bounded: the system returns to a working demonstration state in ten minutes, having lost the alerts and cases created since the last restore point. For a prototype, that is an acceptable loss. For a real deployment it would not be, which is why V1 scope includes a real retention and backup policy.

## 4. Recovery Procedures

### 4.1 Rebuild from seed — the primary path

```bash
pnpm db:migrate
pnpm generate:data          # seed 26184, deterministic
python scripts/evaluation/signal_check.py    # gate
python scripts/evaluation/pii_scan.py        # gate
pnpm db:seed                # verifies manifest checksums
pnpm train:model
pnpm evaluate               # writes model_metrics
```

Roughly five minutes end to end. The two gates run in recovery exactly as they run in normal setup — a recovery path that skips validation is how a corrupted corpus gets promoted to primary.

### 4.2 Point-in-time restore

```bash
neon branches create --name recovery --parent main --timestamp "2026-09-15T04:00:00Z"
# verify against the recovery branch
pnpm test:smoke --database-url "$RECOVERY_URL"
# promote only after verification
```

Always restore to a branch and verify before promoting. Restoring directly over the primary removes the ability to compare the two, which is the only way to tell whether the restore point was actually before the problem.

### 4.3 Model artefact recovery

```bash
docker pull ghcr.io/<org>/cyberpulse-ml:<previous-sha>    # fastest
# or
pnpm train:model && pnpm evaluate                          # ~2 min, gates enforced
```

Redeploying the previous image tag also rolls back `model_version`, so the reported version and the running model stay consistent — there is no path where they diverge.

## 5. Verification

A backup that has never been restored is a hypothesis.

| Check | Frequency | Method |
|---|---|---|
| Rebuild-from-seed produces an identical corpus | Every CI run | Manifest checksum comparison (TC-DATA-002) |
| Migrations apply cleanly to an empty database | Every CI run | Migration job |
| Model retraining clears all metric gates | Every model change | `evaluate.py` exit code |
| Point-in-time restore works | Once per phase | Restore to a branch, run the smoke suite, discard |
| Full recovery within RTO | Before the finale | Timed rehearsal of §4.1 |

The last row is the one that matters. It is scheduled as a Phase 7 task specifically because an untested recovery procedure discovered during a finale is not a recovery procedure.

## 6. What Is Not Backed Up, Deliberately

| Not backed up | Reason |
|---|---|
| Application logs | Platform retention is sufficient; no long-term value |
| `analytics_events` | Measurement data, regenerable by re-running rehearsals |
| Preview environment databases | Ephemeral by design, destroyed on merge |
| Local development databases | Individual, rebuildable in three minutes |
| Container build caches | Rebuildable |

---

## 7. Prototype Limitations

| Limitation | Impact | V1 remedy |
|---|---|---|
| Backup depends entirely on the Neon tier's retention | Loss beyond the window is unrecoverable | Scheduled logical dumps to independent storage |
| No off-provider copy | Provider-level failure is unrecoverable | Cross-provider backup |
| No automated restore verification | Restores are tested manually, per phase | Automated weekly restore drill |
| No retention policy on `audit_events` | Grows unbounded | Retention plus archival (G-4) |
| No encryption of backups under our own key | Provider-managed only | Customer-managed keys |

All five are acceptable for a prototype holding synthetic data. None would be acceptable for a deployment holding real case data, and the classification gate in `architecture/integrations.md` §3.1 is the mechanism that forces the question before that transition.
