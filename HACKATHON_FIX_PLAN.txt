======================================================================
1. PURPOSE, SCOPE AND WORKING RULES
======================================================================

Objective
---------
Make the submission technically credible, internally consistent, accessible
and reliable for a short synthetic-data demonstration. Correct predictive
validity before adding features or strengthening performance claims.

This document is a plan, not a record of completed fixes. Creating this
document does not authorize code changes, dependency installation, data
regeneration, model retraining, migrations, deployment or external messages.
Wait for explicit implementation approval.

Priorities
----------
P0: Submission blockers: prediction validity, truthful claims, security
    defects, vulnerable dependencies and reproducible demo reliability.
P1: Important completeness, usability and maintainability improvements.
P2: Optional polish and pilot preparation.
P3: Production hardening; outside the synthetic hackathon release.

Execution rules once implementation is approved
-----------------------------------------------
- Preserve the existing uncommitted model/data changes. Establish a baseline
  before regenerating anything; do not overwrite them without resolving
  their intended status with the user.
- Use an isolated test database for mutations, resets, migrations and E2E.
- Read relevant REQUIREMENTS.md, FEATURE_SPECIFICATIONS.md,
  ACCEPTANCE_CRITERIA.md, ADRs and .claude/rules before each work package.
- Update requirements and decision records when deliberately narrowing a
  promise. Do not silently remove a requirement to make a check pass.
- Keep API/schema contracts in packages/shared; preserve the training
  features.py symlink and the database-free ML serving boundary.
- Write regression tests for substantive bugs and security changes.
- Never invent predictions, pad explanations or lower release thresholds
  merely to obtain a passing evaluation.
- Publish synthetic-data limitations beside metrics. No real-data,
  government-endorsement, external-delivery or financial-impact claims
  without evidence.
- Keep documentation, tests and implementation aligned in each change.

F01 - DEFINE OBSERVATION TIME AND REMOVE FUTURE-INFORMATION LEAKAGE
Priority: P0 | Owner: ML + backend | Estimate: 1-3 engineer-days
Dependencies: baseline preservation and agreed forecast semantics

Evidence:
- predictionService.ts fetches all linked transactions without a cutoff.
- features.py counts velocity in the hour after complaint filing.
- Audit counted 109 post-filing linked transactions across 72 complaints.

Plan:
1. Define an explicit observation/asOf timestamp. Default historical replay
   to complaint time; any later replay must declare its observation time.
2. Distinguish event time from information availability. In synthetic data,
   document any assumption that records are immediately observable.
3. Restrict transactions, account histories, withdrawal histories and graph
   evidence to records available by the observation timestamp.
4. Compute velocity over a trailing observation window. Anchor recency,
   account age and forecast horizon to the same reference time.
5. Use identical temporal semantics in training and serving.
6. Exclude already-completed outcomes from future-event targets or introduce
   an explicit no-future-event outcome. Do not force every case to have a
   future cash-out prediction.
7. Treat information from later observations as a new forecast, not a revised
   account of what was knowable at filing time.

Likely files:
  apps/web/services/predictionService.ts
  apps/web/services/hotspotService.ts
  apps/web/services/transactionService.ts
  apps/ml-service/app/engine/features.py
  apps/ml-service/training/generate_training_data.py
  packages/shared/schemas/*predict*.schema.json

Acceptance:
- Adding records after asOf cannot change that historical forecast.
- Boundary timestamps, missing records and already-withdrawn cases have
  explicit tested behavior.
- Training/serving feature vectors agree for the same observed inputs.
- UI/API identify the observation timestamp and forecast horizon.

F03 - EVALUATE THE EXACT SERVED PIPELINE
Priority: P0 | Owner: ML | Estimate: 1.5-3 days
Dependencies: F01, F02

Plan:
1. Extract reusable scoring/ranking logic so evaluation invokes the same
   blend, candidate ordering and temporal-window selection as serving.
2. Report classifier probability metrics separately from composite-score
   ranking metrics. Do not apply classifier calibration results to the blend.
3. Measure top-1/3/5 ranking, candidate recall, temporal coverage and joint
   location-plus-window success at the actual selected location.
4. Report lead-time distributions and the fraction of complaints with an
   actionable future window; include missed and already-completed outcomes.
5. Evaluate random, nearest-cell, historical-frequency and logistic baselines
   with the same candidates, observation time, labels and denominators.
6. Add complaint-level uncertainty estimates and failure examples. Use a
   forward-time holdout; assess geography holdout if the corpus supports it.
7. Keep a final test set untouched by model selection. Do not tune repeatedly
   on the published holdout.
8. Accept the simpler baseline if it performs as well or better. If the
   claimed improvement is unsupported, narrow the submission claim.
